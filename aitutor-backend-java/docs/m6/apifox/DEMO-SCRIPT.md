# LeapMind M6 Apifox 演示讲稿

建议时长：8–10 分钟。演示账号仅使用本机隔离数据库中的专用测试账号，凭据保存在 Apifox 本地环境中，不写入仓库：

```text
开发环境：http://localhost:8080
username：demo_user
password：<本地测试密码>
```

## 演示前 2 分钟检查

1. 在 Apifox 选择“开发环境”，确认前置 URL 是 `http://localhost:8080`，不要选择“本地 Mock”。
2. 环境变量填写专用本地测试账号和密码，不在屏幕录制或提交中展示具体值。
3. 先发送“登录并提取 Token/UserId”，确认返回 HTTP 200。
4. 确认环境变量自动出现 `accessToken` 和登录响应返回的 `userId`。
5. “首次写入 → 原样重试 → 同 ID 改内容”必须连续执行。

## 1. 开场与模块定位（约 45 秒）

### 屏幕操作

打开 Apifox 项目左侧的 `LeapMind M6 上下文记忆与用户画像演示` 集合，先停留在接口目录。

### 讲稿

> 接下来演示 LeapMind 的 M6 上下文记忆和用户画像模块。它不直接负责生成课程内容，而是负责接收各学习模块产生的行为事件，把这些事件沉淀为可追溯的学习事实，并向讲解、授课和问答模块提供最小化的用户上下文。
>
> 这套接口主要分为三部分：第一是身份认证；第二是学习事件采集；第三是画像、场景摘要和知识点状态查询。最后我还会展示它的权限与数据安全边界。

## 1.5 本周完成的工作（约 60–90 秒）

### 屏幕操作

停留在 Apifox 接口目录，不需要快速切换页面。讲完后再进入环境说明。

### 大白话讲稿

> 这周我主要做的是 M6 用户画像模块。简单来说，就是让系统不只知道“这个用户是谁”，还能够记住他最近学了什么、哪些题做错了、哪些知识点容易困惑，以及他更喜欢什么样的讲解方式。
>
> 第一，我先把其他模块传过来的学习行为统一成了一套格式。比如做题、请求讲解、复习知识点，这些行为都可以作为学习事件交给 M6，不需要每个模块各写一套接口。
>
> 第二，我补了防重复和防错误的处理。同一条事件因为网络问题重复发送，系统只记录一次；如果有人用了相同的事件编号，但是修改了内容，系统会直接报冲突，不会悄悄覆盖原来的数据。
>
> 第三，我补了用户画像的查询接口。其他模块可以查询完整画像，也可以只查询当前讲解场景需要的内容，或者只看某几个知识点的掌握情况。这样不用每次把所有用户信息都传过去。
>
> 第四，我做了权限和隐私保护。用户没登录不能查看画像；登录以后也只能查看自己的画像。像密码、Token 这类敏感字段如果被误放进学习事件里，接口会直接拒绝。
>
> 最后，我把接口整理成了 Apifox 演示集合，准备了真实请求、自动登录、结果断言和离线响应示例。现在可以比较直观地演示事件第一次接收、重复识别、内容冲突、批量部分失败以及画像查询这些流程。
>
> 目前已经完成的是事件接收、校验、存储和查询这条基础链路。画像自动计算和正式发布还没有完全接通，所以新用户查询时可能会返回 NOT_READY。这个状态不是接口坏了，而是系统明确告诉下游：现在还没有一份可以放心使用的画像。

### 更短的 30 秒版本

如果汇报时间很紧，可以只说：

> 这周我主要完成了 M6 用户画像模块的基础链路。系统现在可以统一接收做题、讲解和复习等学习行为，能防止事件被重复记录，也能发现同一个事件编号内容被修改的问题。同时补了完整画像、场景摘要和知识点查询接口，并加上了登录校验、只能查看本人画像以及敏感字段拒绝。最后我整理了 Apifox 演示集合。当前事件接收和查询已经能跑通，画像自动计算部分还需要继续接线，所以新用户可能返回 NOT_READY。

## 2. 环境说明（约 30 秒）

### 屏幕操作

点击顶部环境，展示当前选中“开发环境”和 `http://localhost:8080`，随后收起环境菜单。不要展开密码或 Token 的具体值。

### 讲稿

> 当前连接的是本机真实 Java 后端，地址是 localhost 8080，不是 Apifox 随机 Mock。数据库也是为本次演示单独启动的本地隔离数据库，因此下面的事件写入、幂等判断和权限校验都是真实执行结果。

## 3. 登录并自动保存上下文（约 50 秒）

### 屏幕操作

进入 `00 登录与环境 → 登录并提取 Token/UserId`，展示请求体中的 `{{username}}`、`{{password}}`，点击“发送”。

### 预期结果

- HTTP 200；
- `message` 为“登录成功”；
- `data.token` 有值；
- `data.userInfo.id` 为当前演示账号的用户 ID；
- 右侧两个断言通过。

### 讲稿

> 第一步先登录。账号密码来自 Apifox 环境变量，不直接写死在接口里。登录成功后，后置脚本会自动提取 Token 和用户 ID，保存为 `accessToken` 和 `userId`。后续所有 M6 请求都会继承 Bearer Token，同时使用当前用户 ID，这样演示过程中不用手工复制凭据。

## 4. 首次写入学习事件（约 60 秒）

### 屏幕操作

进入 `01 事件采集 → 1. 首次写入 - ACCEPTED`，快速展示事件体，然后点击“发送”。

### 重点展示字段

- `eventType=answer_question`；
- `sourceModule=M1`；
- `kpId=101`；
- `data.isCorrect=false`；
- `confusionTag=concept_unclear`。

### 预期结果

- HTTP 200；
- `eventStatus=ACCEPTED`；
- `duplicate=false`；
- `profileUpdateStatus=PENDING`。

### 讲稿

> 这是一条来自 M1 练习模块的答题事件。它包含用户、知识点、发生时间和必要的学习结果，但不会把密码、Token 或大段隐私文本混入画像数据。
>
> 前置脚本会为每次主演示生成新的 eventId。服务返回 ACCEPTED，表示事实已经被可靠接收；PENDING 表示画像投影可以在后续异步计算，而不是阻塞用户当前的学习操作。

## 5. 幂等重试（约 45 秒）

### 屏幕操作

立即进入 `2. 原样重试 - DUPLICATE`，不要改请求体，直接发送。

### 预期结果

- HTTP 200；
- `eventStatus=DUPLICATE`；
- `duplicate=true`。

### 讲稿

> 网络调用可能因为超时而重试，所以系统不能把同一次答题重复记账。这里使用完全相同的 eventId 和内容再次请求，服务不会新增第二条事实，而是明确返回 DUPLICATE。这就是事件接口的幂等保障。

## 6. 同一 ID 的冲突保护（约 45 秒）

### 屏幕操作

进入 `3. 同 ID 改内容 - 409 CONFLICT`。指出这里只把 `isCorrect` 从 false 改成了 true，然后发送。

### 预期结果

- HTTP 409；
- `data.errorCode=PROFILE_IDEMPOTENCY_CONFLICT`。

### 讲稿

> 如果调用方复用同一个 eventId，却偷偷修改业务内容，系统不会覆盖原事实。这里同一个事件从答错变成答对，因此返回 409 幂等冲突。这样可以避免重试、并发或错误调用污染用户画像。

## 7. 隐私与严格字段校验（约 40 秒）

### 屏幕操作

进入 `4. 敏感字段拒绝 - 400`，展示 `data.authorization` 是演示占位值，点击发送。

### 预期结果

- HTTP 400；
- `data.errorCode=PROFILE_EVENT_INVALID`。

### 讲稿

> M6 对事件数据采用严格白名单。这里故意把 authorization 字段放入学习数据，即使它只是演示占位值，也会被拒绝。这个设计防止认证凭据或未知字段被错误沉淀到长期画像中。

## 8. 批量事件的部分失败隔离（约 50 秒）

### 屏幕操作

进入 `5. 批量事件 - 部分失败`，指出第一条来源为 M1，第二条故意把答题事件来源写成 M2，点击发送。

### 预期结果

- HTTP 200；
- 第 0 项 `ACCEPTED`；
- 第 1 项 `FAILED`；
- 两项顺序与输入一致。

### 讲稿

> 批量接口采用条目级结果。第一条合法事件正常接收，第二条来源模块不符合契约，因此单独失败。系统不会因为一条坏数据就抹掉整批合法事件，同时返回结果仍保持原始顺序，方便上游精确重试。

## 9. 完整画像与 NOT_READY 语义（约 55 秒）

### 屏幕操作

进入 `02 画像查询 → 1. 完整画像`，点击发送。

### 当前真实预期

- HTTP 200；
- `profileStatus=NOT_READY`；
- `profileVersion=0`。

### 讲稿

> 接下来查询完整画像。当前隔离数据库刚刚创建，事件已经成功接收，但画像计算与发布链路还没有产出可发布快照，因此这里返回 NOT_READY。
>
> NOT_READY 不是接口报错，而是一个明确的业务状态：系统宁可告诉下游“目前证据不足或尚未计算”，也不会编造一份画像。正式具备投影结果后，同一个接口会返回 READY 或 STALE，以及学习偏好、近期关注点、困惑和知识点掌握度。

如需展示 READY 的完整结构，打开 `1. 完整画像` 下保存的 `200 READY（离线示例）`，并明确说明它是契约示例，不是本次实时计算结果。

## 10. 场景化摘要与知识点查询（约 50 秒）

### 屏幕操作

依次打开：

1. `2. 讲解场景摘要`；
2. `3. 知识点状态`。

可以发送真实请求，也可以打开保存的离线响应示例展示 READY 数据结构。

### 讲稿

> 下游模块通常不需要读取整份画像。讲解模块可以通过 explaining 场景摘要，只获取当前知识点、近期困惑和内容偏好；知识点接口则支持一次查询多个 kpId。
>
> 这种按场景最小化返回的设计减少了模块耦合，也避免把无关的用户信息扩散给所有下游服务。

## 11. 401 与 403 权限边界（约 45 秒）

### 屏幕操作

依次发送：

1. `03 权限与协议边界 → 1. 未登录访问 - 401`；
2. `2. 越权访问其他用户 - 403`。

### 讲稿

> 最后展示访问控制。第一条请求故意不带 Token，所以返回 401；第二条带着合法 Token，但请求另一个用户的画像，因此返回 403。
>
> 可以把这条规则概括为：未登录不能读，登录后也只能读自己的画像。认证和 self-only 授权是两道独立边界。

## 12. 收尾（约 30 秒）

### 讲稿

> 这次演示展示了 M6 的核心闭环：统一接收学习事件，通过幂等和严格校验保证事实可靠，再以完整画像、场景摘要和知识点状态服务其他模块，同时用认证、数据隔离和敏感字段拒绝保护用户信息。
>
> 当前真实环境已经验证了登录、首次接收、重复识别和 NOT_READY 降级语义；画像计算器完成生产接线后，无需改变上游事件契约和下游查询接口，就能逐步发布 READY 画像。

## 现场故障备用话术

### 后端突然连接失败

> 当前现场服务连接异常，我切换到预先保存的契约响应示例。下面展示的是接口定义与预期响应，不把它表述为实时执行结果。

随后不要点击“发送”，只打开各请求保存的“离线示例”。

### 画像返回 NOT_READY

不要说“画像接口坏了”，使用：

> 事件采集和画像发布是解耦的。NOT_READY 表示当前没有可安全发布的画像快照，下游应采用通用策略降级，而不是使用未经验证的数据。

### 登录断言失败

1. 确认选中“开发环境”，不是“本地 Mock”；
2. 确认 URL 为 `http://localhost:8080`；
3. 确认环境中已填写专用本地测试账号和密码；
4. 重新发送登录请求。
